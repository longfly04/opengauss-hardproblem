# openGauss 内存管理技术验证方案

## 项目设计背景与目标

本项目设计为一套 **基于Docker、OpenEular 兼容** 的 openGauss 实验环境，旨在围绕内存管理、work\_mem / memory pool 观测、执行计划离线分析和内核实验做部署、压测、观测、对比与源码调试。项目采用双运行模式（stock mode 和 source mode），共享同一套 benchmark / observability / experiment 脚本，为内存管理相关的技术研发提供可复现、可对比的实验平台。

## 技术诉求映射分析

### 难题1：内存池自适应管理技术

#### 技术诉求拆解

1. **相同内存硬件规格和物理内存使用上限下**，在某 TOP 大行对账场景下，通过自适应管理对动态内存池和共享内存池的自动化管理，**落盘降低 90% 以上，性能提升 10X**。

2. **在低规格内存配置下**（16U/32GB 及以下），使用 sysbench 构建高并发的 TP 流量，同时瞬间注入包含大内存使用算子（sort、hashjoin、seqscan）的慢 SQL，通过内存池自适应调整快速介入，**避免动态内存瞬间过载，对 TPS 的影响抖动控制在 10% 以内**。

#### 项目支撑能力

1. **可观测能力**：
   - 共享内存与会话内存观测：通过 `lab_obs.shared_memory_contexts`、`lab_obs.shared_memory_totals`、`lab_obs.session_memory_summary` 等视图提供实时采样。
   - spill 与 temp I/O 观测：通过 `lab_obs.database_spill_stats` 和 exporter 采集的 `temp_files/temp_bytes` 提供落盘观测。
   - 场景化压测与抖动验证：通过 `run-scenario.sh` 编排场景，`validate-targets.sh` 产出 `tps_jitter_pct` 和 `peak_temp_bytes` 等验证指标。

2. **实验验证流程**：
   - 支持 sysbench 构建高并发 TP 流量。
   - 支持注入包含大内存使用算子的慢 SQL（如 TPCH 查询）。
   - 提供详细的执行计划分析，包括算子级内存使用和落盘统计。
   - 生成验证摘要和对比报告，量化性能提升和落盘减少。

3. **源码证据位置**：
   - 内存池与内存上限相关 GUC：`src/common/backend/utils/misc/guc/guc_memory.cpp`
   - 过载逃生/拒绝接入/清理连接：`src/common/backend/utils/mmgr/mem_snapshot.cpp`

#### 当前缺口

- 尚未实现“动态池↔共享池自动再分配算法控制器”，当前是验证平台，不是自治控制器。
- 缺少“在线策略引擎”把观测信号自动转化为 GUC/配额调控动作。

### 难题2：内存动态调整和优雅回收技术

#### 技术诉求拆解

1. **技术目标1**：基于 workprofile、内存分配和 IO 投入产出比、活跃会话数、剩余内存等多个负载特征计算当前每个会话的内存上限（bound），根据负载变化周期性实时调整 bound，确保 bound 符合当前负载需求；按照调整后的 bound，支持对会话上使用的内存（执行计划，syscache，存储过程，算子）进行优雅回收降低到 bound 值，全程对用户无感知无侵入。

2. **技术目标2**：在 8U64GB 规格以上服务器，安装 openGauss 数据库，使用 sysbench 作为标准 TPS 测试工具进行测试验证，实现：
   - 在 sysbench 构建高并发的 TP 流量场景下，快速注入包含大内存使用算子（sort、hashjoin、seqscan）的慢 SQL（如 TPCH 模型），对 sysbench TPS 的影响抖动控制在 10% 以内；
   - 在慢 SQL（如 TPCH 模型）业务占用内存超 90% 场景下，注入高并发 sysbench 业务，sysbench TPS 可以达到无背景慢 SQL 场景的 90% 以上。

#### 项目支撑能力

1. **会话内存与活跃状态联合观测**：
   - 通过 `lab_obs.session_memory_with_activity` 关联 `pg_stat_activity`，提供会话内存与活跃状态的联合视图。
   - 通过 `sample-db-memory.sh` 输出 `session_used_sum_bytes/session_used_max_bytes/active_sessions/temp_bytes` 等指标。

2. **参数观测与配置**：
   - 通过 `lab_obs.selected_settings` 观测关键内存参数配置。
   - 支持不同参数组的 A/B 对比验证。

3. **算子级内存使用分析**：
   - 通过 `run-tpch.sh` 采集 `EXPLAIN ANALYZE` 执行计划。
   - 通过 `profile-tpch.sh` 解析 Hash Join/Sort/Seq Scan 等算子的内存使用信息。

4. **源码证据位置**：
   - Query memory 计算主路径：`src/gausskernel/cbb/workload/memctl.cpp`
   - 运行时可用内存/statement_mem 协同：`src/gausskernel/cbb/workload/dywlm_client.cpp`
   - 统计侧读取 query_mem：`src/gausskernel/cbb/workload/statctl.cpp`
   - EXPLAIN 与算子内存输出链路：`src/include/executor/instrument.h`、`src/gausskernel/runtime/executor/nodeSort.cpp`、`src/gausskernel/optimizer/commands/explain.cpp`

#### 当前缺口

- 尚未实现“会话级 bound 预测算法”（多维负载特征建模 + 在线推断）。
- 尚未实现“活跃会话优雅回收控制器”（当前上游过载路径偏 kill/reject）。

## 验证方案设计

### 难题1验证方案

1. **实验环境准备**：
   - 使用 stock mode 构建可信基线镜像。
   - 配置 16U/32GB 低规格内存环境。
   - 准备 sysbench 数据和 TPCH 数据。

2. **基准测试**：
   - 运行 `tpcc-steady` 场景，记录 TPS 基线。
   - 运行 `tpch-baseline` 场景，记录落盘情况和性能。

3. **压力注入测试**：
   - 运行 `tpcc-plus-tpch-injection` 场景，模拟高并发 TP 流量 + 突发慢 SQL 注入。
   - 记录 TPS 抖动、落盘情况和性能变化。

4. **参数调优对比**：
   - 调整内存池相关参数（如 `memorypool_size`、`work_mem`、`query_mem` 等）。
   - 重新运行场景，对比不同参数配置下的性能和落盘情况。

5. **数据分析**：
   - 使用 Grafana 面板分析内存使用、落盘情况和 TPS 变化。
   - 生成验证摘要和对比报告，量化落盘减少和性能提升。

### 难题2验证方案

1. **实验环境准备**：
   - 使用 stock mode 构建可信基线镜像。
   - 配置 8U64GB 及以上规格内存环境。
   - 准备 sysbench 数据和 TPCH 数据。

2. **基准测试**：
   - 运行 `tpcc-steady` 场景，记录 TPS 基线。

3. **压力测试**：
   - 运行 `slow-sql-under-tp` 场景，模拟高并发 TP 流量 + 慢 SQL 注入。
   - 记录 TPS 抖动情况。

4. **内存占用测试**：
   - 运行 TPCH 查询，使内存占用超 90%。
   - 注入高并发 sysbench 业务，记录 TPS 表现。

5. **参数调优对比**：
   - 调整会话内存上限相关参数。
   - 重新运行场景，对比不同参数配置下的 TPS 表现。

6. **数据分析**：
   - 使用 Grafana 面板分析会话内存使用、活跃会话数和 TPS 变化。
   - 生成验证摘要和对比报告，评估 TPS 影响抖动和恢复情况。

## 保障措施

1. **可复现性保障**：
   - 双运行模式（stock/source）确保实验环境的一致性。
   - 标准化的场景配置和实验流程，确保实验可重复。
   - 详细的运行产物和验证摘要，提供可追溯的实验证据。

2. **观测能力保障**：
   - 全面的 SQL 观测视图，覆盖共享内存、会话内存、temp I/O 等关键指标。
   - 统一的 Prometheus exporter，将数据库指标和运行产物暴露为可监控指标。
   - 丰富的 Grafana 面板，直观展示内存使用、性能变化和执行计划分析结果。

3. **验证方法保障**：
   - 标准化的验证脚本，自动计算 TPS 抖动、落盘情况等关键指标。
   - 离线执行计划分析，提供算子级内存使用和落盘证据。
   - 详细的对比报告，量化性能提升和落盘减少。

4. **源码对接保障**：
   - 明确的上游源码证据位置，为内核改造提供参考。
   - source mode 支持源码开发和调试，便于快速验证内核改动。
   - 完整的构建和部署流程，确保源码改动可快速集成到实验环境。

## 结论

本项目已具备 **难题1/难题2的验证实验室基础**：可构造压力场景、采集关键信号、输出对比证据，形成“参数->会话内存压力->spill->TPS”的因果证据链。通过本项目的实验平台，可以验证内存池自适应管理和内存动态调整/优雅回收技术的效果，为最终实现“相同内存下达成最大吞吐；或相同吞吐下使用最少内存”的目标提供有力支持。

虽然当前项目尚未实现完全自治的在线调参与优雅回收算法，但已为这些能力的研发提供了坚实的验证基础。通过持续的内核改造和实验验证，有望逐步实现难题中提出的技术目标。
